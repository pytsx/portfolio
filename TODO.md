# Auditoria técnica do Next.js no projeto `pytsx/portfolio`

Repositório: [pytsx/portfolio](https://github.com/pytsx/portfolio?utm_source=chatgpt.com) · Branch `main` · Next.js 16.4.3

Sua aplicação já utiliza conceitos importantes e relativamente avançados do Next.js: App Router, React Server Components, Server Actions, Cache Components, Suspense, Route Groups e autenticação no servidor.

O ponto principal da análise não é adicionar recursos indiscriminadamente. É identificar onde a arquitetura atual não aproveita completamente o Next.js e onde algumas decisões podem provocar problemas de SEO, desempenho, segurança ou manutenção.

## 1. Diagnóstico geral

| Área                     | Avaliação inicial                               |
| ------------------------ | ----------------------------------------------- |
| App Router e organização | Boa base                                        |
| Server Components        | Bem aproveitados                                |
| Streaming e Suspense     | Implementados, com oportunidades de refinamento |
| Cache Components         | Implementados de forma explícita                |
| Server Actions           | Bem estruturadas                                |
| SEO e Metadata           | Deficiências confirmadas                        |
| Roteamento dinâmico      | Funcional, mas pode ser otimizado               |
| Autenticação             | Boa separação de responsabilidades              |
| Consulta ao Firestore    | Oportunidade relevante de otimização            |
| Testes e observabilidade | Cobertura a ampliar                             |

Uma característica importante: seu portfólio deixou de ser apenas um site com páginas fixas. Ele funciona como um CMS baseado em blocos, com publicação dinâmica de conteúdo.

Isso muda quais recursos do Next.js são mais valiosos. A prioridade passa a ser renderização pública eficiente, indexação, publicação e invalidação inteligente de cache.

## 2. Problemas concretos que encontrei

### 2.1. Metadata e SEO das páginas públicas

Prioridade crítica

Arquivo: `app/(public)/layout.tsx`

Seu layout público declara:

```
export const metadata: Metadata = {
  title: "Create Next App",
  description: "Generated by create next app",
}
```

Embora `app/layout.tsx` já gere metadata usando as configurações do portfólio, o layout público sobrescreve esses campos. Além disso, sua rota `[...path]` não possui `generateMetadata()`.

Consequência: um artigo publicado em `/blog/meu-artigo` não recebe automaticamente título, descrição e metadados de compartilhamento próprios. Isso prejudica a apresentação em mecanismos de busca e redes sociais.

Como eu corrigiria:

- Remover os metadados de exemplo do layout público.
- Adicionar `generateMetadata()` à home e à rota dinâmica.
- Incluir descrição, imagem de capa e informações de SEO no modelo de cada página.
- Gerar `canonical`, Open Graph e Twitter Cards.

O Next.js já oferece essa infraestrutura nativamente.&#x20;

Next.js+1



### 2.2. Você está enviando conteúdo completo das páginas para a sidebar

Prioridade alta

Arquivos: `app/(protected)/layout.tsx` e `app/(protected)/_src/admin-sidebar.tsx`

O layout faz:

```
const [groups, pages] = await Promise.all([
  groupRepository.list(),
  pageRepository.list(),
])

return (
  <AdminSidebar
    groups={groups}
    pages={pages}
    user={user}
  />
)
```

Entretanto, `AdminSidebar` é um Client Component, e os tipos `ContentPage` e `PageGroup` incluem `content`, ou seja, os documentos inteiros do editor.

A sidebar precisa apenas de informações como ID, título, grupo, slug e indicação de página principal.

Atualmente, o código passa todo o conteúdo de todas as páginas e grupos pela fronteira entre Server e Client Components, mesmo quando o usuário só precisa visualizar a navegação.

Isso pode aumentar significativamente o payload React Server Components conforme o portfólio crescer.

Eu criaria DTOs específicos:

```
type SidebarPage = {
  id: string
  title: string
  groupId?: string
  groupSlug?: string
  isHome: boolean
}

type SidebarGroup = {
  id: string
  title: string
  slug: string
  parentId?: string
}
```

E faria o mapeamento no servidor, antes de passar os dados para a sidebar.

Esse é um exemplo de como aproveitar melhor a separação entre Server Components e Client Components.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nextjs.org\&sz=32)

Next.js



### 2.3. Consultas duplicadas ao Firestore na administração

Prioridade alta

O layout protegido busca todas as páginas e grupos para montar a sidebar. Depois, rotas como `/admin`, `/admin/pages` e `/admin/groups` voltam a consultar esses repositórios.

Sua autenticação já utiliza corretamente `cache()` do React, mas as consultas `pageRepository.list()` e `groupRepository.list()` não possuem a mesma deduplicação por requisição.

Isso pode causar leituras redundantes do Firestore.

Melhoria: criar uma camada de leitura memoizada por requisição com `React.cache`, sem compartilhar informações autenticadas no cache público.

```
import "server-only"
import { cache } from "react"

export const getAdminNavigation = cache(async () => {
  const [groups, pages] = await Promise.all([
    groupRepository.list(),
    pageRepository.list(),
  ])

  return {
    groups: groups.map(({ id, title, slug, parentId }) => ({
      id, title, slug, parentId,
    })),
    pages: pages.map(({ id, title, groupId, groupSlug, isHome }) => ({
      id, title, groupId, groupSlug, isHome,
    })),
  }
})
```

Para obter o melhor resultado, eu também ajustaria o repositório para buscar documentos leves destinados à navegação.

### 2.4. Toda página pública depende da listagem completa de páginas

Prioridade alta

Arquivos: `lib/pages/index.ts` e `app/(public)/[...path]/page.tsx`

Seu método principal faz:

```
const snapshot = await getDocs(
  query(
    collection(db, "pages"),
    where("visibility", "==", "public")
  )
)
```

Depois, o roteamento usa essa coleção para localizar a página correspondente.

Isso funciona bem com poucas páginas e é atenuado pelo cache remoto. Mas existe um problema de escalabilidade: mesmo para abrir um único artigo, o sistema depende de um conjunto que contém o conteúdo completo de todos os artigos públicos.

Eu separaria:

1. Índice de navegação: dados mínimos das páginas, sem os blocos.
2. Documento individual: conteúdo completo da página solicitado por ID.
3. Coleções: consultas de listagem com filtros e paginação.

Você também chama `resolvePageCollections()` em todas as páginas, inclusive naquelas que não possuem blocos `pageCollection`. Essa função volta a solicitar a lista de páginas e grupos.

Seria melhor verificar a presença desse tipo de bloco antes de resolver coleções.

O resultado seria menor consumo de memória, menos serialização de dados e maior previsibilidade quando o conteúdo crescer.

### 2.5. `useSearchParams` na tela de login sem Suspense próprio

Revisar

Arquivo: `app/(auth)/signin/page.tsx`

A página utiliza `useSearchParams()` diretamente no componente principal marcado com `"use client"`.

Em páginas elegíveis à pré-renderização estática, esse hook precisa estar protegido por um limite de `Suspense`; caso contrário, o build de produção pode falhar.

A documentação do Next.js é explícita sobre essa condição.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nextjs.org\&sz=32)

Next.js



A correção mais limpa é manter a página como Server Component e passar `next` para um componente de formulário interativo, ou isolar o componente que usa `useSearchParams` dentro de `Suspense`.

Esse é um risco identificado por inspeção; não executei um build para afirmar que ele já está falhando no seu ambiente.

### 2.6. As imagens publicadas não usam a otimização nativa

Arquivo: `components/block-renderer.tsx`

Você desabilitou a regra `@next/next/no-img-element` e renderiza imagens dos blocos com `<img>`.

Essa escolha evita configurações adicionais para URLs dinâmicas, mas deixa de aproveitar o pipeline de imagens do Next.js.

Eu evoluiria o schema dos blocos para armazenar dimensões, texto alternativo e, opcionalmente, prioridade de carregamento. Depois utilizaria `next/image` com domínios de origem permitidos.

Isso permite gerar tamanhos responsivos e reservar o espaço das imagens, reduzindo mudanças inesperadas no layout.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nextjs.org\&sz=32)

Next.js



### 2.7. Você está usando Server Action para consultar a sessão no navegador

Arquivos: `app/(public)/_src/account-menu.tsx` e `lib/auth/actions.ts`

O `AccountMenu` executa `getSessionUser()` dentro de um `useEffect`, depois que a interface é hidratada.

Isso significa uma chamada adicional ao servidor para descobrir se o visitante está autenticado. No Next.js, Server Functions invocadas pelo cliente usam requisições POST, mesmo quando apenas consultam dados.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nextjs.org\&sz=32)

Next.js



Eu consideraria transformar a consulta em um pequeno Server Component, envolvido por `Suspense`, e passar somente os dados mínimos para a parte interativa do menu.

Assim, a consulta de autenticação pode participar do fluxo de renderização do servidor, sem depender de um efeito executado depois do carregamento do JavaScript.

### 2.8. A experiência inicial pode prejudicar a percepção de desempenho

Arquivo: `app/(public)/_src/welcome.tsx`

O componente mostra uma tela de boas-vindas que cobre toda a viewport durante 1,5 segundo. Ela é independente de o conteúdo real já ter terminado de carregar.

O resultado é que você pode entregar HTML rapidamente com Server Components e, ainda assim, impedir visualmente que o visitante interaja com a página.

Minha sugestão é remover essa tela como etapa obrigatória do carregamento, preservando a animação de texto dentro da própria home. Assim, você mantém a identidade visual sem bloquear a navegação.

## 3. Conceitos do Next.js que você ainda poderia aplicar

Aqui estão as funcionalidades que considero mais interessantes para a evolução do portfólio.

Metadata API + sitemap dinâmico

Gere `app/sitemap.ts`, `app/robots.ts` e metadata individual por página. O sitemap deve considerar a árvore de grupos e incluir apenas URLs públicas acessíveis.

Prioridade: muito alta · SEO e descoberta de conteúdo

Open Graph Image / ImageResponse

Gere imagens de compartilhamento automaticamente com base no título e na identidade do site. Um artigo poderia ter uma capa social gerada mesmo sem uma imagem enviada pelo editor.

Prioridade: alta · Compartilhamento e apresentação

`generateStaticParams()` seletivo

Permite pré-renderizar páginas conhecidas durante o build. Para o seu CMS, eu usaria apenas onde a pré-renderização trouxer ganho real, mantendo o suporte a novas páginas publicadas sem redeploy.

Prioridade: média · Pré-renderização&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nextjs.org\&sz=32)

Next.js



`draftMode()` para pré-visualização

Permita visualizar conteúdo não publicado usando o mesmo renderer público, sem torná-lo acessível a visitantes anônimos. A sessão administrativa deverá continuar sendo verificada.

Prioridade: média · Experiência de edição

Route Handlers para RSS

Uma rota `app/rss.xml/route.ts` poderia produzir um feed de publicações diretamente a partir do Firestore, reaproveitando seu modelo de conteúdo.

Prioridade: média · Distribuição do blog

`instrumentation.ts` e Web Vitals

Adicione monitoramento de erros, latência de consultas e métricas reais de carregamento. Isso permitirá comprovar se as otimizações estão funcionando.

Prioridade: média · Observabilidade&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nextjs.org\&sz=32)

Next.js



### E Parallel Routes e Intercepting Routes?

Você ainda não utiliza essas funcionalidades, mas isso não é um defeito arquitetural.

Um caso interessante seria abrir a pré-visualização de uma página em um modal, sobre a listagem administrativa, mantendo o URL navegável e permitindo abrir a mesma página diretamente.

Porém, para o seu estágio atual, não introduziria Parallel Routes apenas para aumentar a quantidade de recursos utilizados.

## 5. Como eu reorganizaria parte do projeto

A estrutura atual por domínio é boa. Não é necessário reescrever a aplicação. Eu acrescentaria uma camada de consultas especializada para cada finalidade:

ESTRUTURA PROPOSTA

```
app/
  sitemap.ts
  robots.ts
  opengraph-image.tsx
  (public)/
    page.tsx
    [...path]/
      page.tsx
  (protected)/
    admin/

lib/
  public/
    page-index.ts
    route-resolver.ts
    metadata.ts
  admin/
    navigation.ts
  pages/
    index.ts
    server.ts
  cache-tags.ts
  firebase/
```

O novo `route-resolver.ts` seria especialmente importante. Atualmente, a resolução da página acontece diretamente no componente da rota pública. Eu extrairia isso para uma função compartilhada por `page.tsx`, `generateMetadata()` e outras funcionalidades, evitando manter duas versões da lógica de resolução de URLs.

Por exemplo:

```
// app/(public)/[...path]/page.tsx

import type { Metadata } from "next"
import { resolvePublicRoute } from "@/lib/public/route-resolver"

type Props = PageProps<"/[...path]">

export async function generateMetadata({
  params,
}: Props): Promise<Metadata> {
  const { path } = await params
  const page = await resolvePublicRoute(path.join("/"))

  if (!page) {
    return { title: "Página não encontrada" }
  }

  return {
    title: page.title,
    description: page.description,
    alternates: {
      canonical: page.canonicalUrl,
    },
    openGraph: {
      title: page.title,
      description: page.description,
      type: "article",
    },
  }
}
```

Nesse exemplo, `description` e `canonicalUrl` são campos que ainda precisariam ser adicionados ou derivados no seu modelo. A ideia é demonstrar como a Metadata API deveria consumir a mesma resolução utilizada pela página pública.

## 7. Conclusão

O que mais chama a atenção no seu projeto é que você já adotou diversas funcionalidades modernas do Next.js 16, mas ainda pode melhorar a forma como elas interagem.

Eu concentraria a próxima evolução em três objetivos:

1. Transformar o CMS em uma plataforma realmente preparada para SEO, com metadata individual, sitemap e compartilhamento de artigos.
2. Reduzir a quantidade de dados processados e enviados desnecessariamente, sobretudo na sidebar administrativa e no roteamento de páginas públicas.
3. Aproveitar melhor as fronteiras entre servidor e cliente, eliminando consultas repetidas e requisições que poderiam ocorrer durante a renderização.

Não recomendaria migrar de framework, substituir o Firebase ou introduzir uma arquitetura muito mais complexa agora. O principal ganho está em refinar a base que você já construiu.

Escopo desta auditoria: análise estática da branch `main`, com comparação à documentação do Next.js 16. Não executei `pnpm build`, testes de carga nem medições de Core Web Vitals; portanto, as oportunidades de desempenho são inferidas do código, e não de benchmarks realizados.
